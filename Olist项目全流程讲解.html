01这个项目是怎么来的

一句话交代背景：我是山东财经大学 2024 级本科生，专业是「大数据管理与应用（金融大数据）卓越创新班」， 2028 届。目标很明确——2026-2027 寒假拿到一份数据分析实习。 这个项目是简历上的第二个项目，用来替换掉原来那个"淘宝用户购买行为分析"。

为什么要换掉原来的项目

原来那个淘宝项目，问题不在做得对不对，而在它长得太像课程作业。HR 和面试官一年要看几百份简历， "某电商平台用户行为分析：PV/UV、转化漏斗、RFM 分层"这套模板他们闭着眼都能背出来。 它证明不了三件事：

  1. 你能不能处理脏数据。教学数据都是洗干净给你的，真实数据不是。
  2. 你会不会定口径。"GMV"这个词背后有十几种算法，选哪一种、为什么，这才是分析师的活。
  3. 你能不能得出一个让业务方不舒服的结论。能算出数的人很多，敢说"这个增长是虚的"的人少。

Olist 这个数据集刚好能同时解决这三点：它是真的（巴西最大的电商平台之一，真实交易数据， 10 万单、7.3 万条评价、8,000 条营销线索），它脏（缺失值、状态混乱、日期错乱、字段拼写错误）， 而且它带营销漏斗——这一点特别关键，大部分电商数据集只有订单，没有"从线索到签约"这一段， 也就没法讲增长质量。

这个项目最后能讲出的那句话 「这家平台的单量两年涨了 9.4 倍，但客单价跌了 13.4%、复购率只有 3.04%—— 它的增长是拉新 + 低价冲量撑起来的，不是复购撑起来的。获客成本一旦上涨，它会立刻失速。」

这句话不是我编的，是三个数字撞出来的（第 11 章会详细拆）。 面试官听到这种话，会立刻知道你是在做分析，不是在做报表。

02要回答的五个问题

整个项目不是"把数据跑一遍看看有啥"，而是带着五个业务问题去查数据。 这五个问题是我在打开 Excel 之前就写在纸上的，后面每一个工具的使用都是为了让这五个问题有答案。

#业务问题翻译成人话主要用到哪张表
1平台盘子多大，钱涨在哪，会不会掉两年做了多少 GMV、多少单；是单量在涨还是单价在涨；有没有大促脉冲订单 + 订单明细
2钱从哪个品类来哪些品类贡献最大；是集中还是长尾；能不能砍掉小品类订单明细 + 商品 + 品类翻译
3客户为什么不回头复购率多少；下过 2 单的人占几个百分点；是不是品类决定的订单 + 客户
4体验是不是复购率低的原因物流延迟会不会导致差评；延迟多久开始崩；影响面多大订单 + 评价
5营销渠道的转化率怎么样哪个渠道招来的卖家最容易签约；签约后有没有真卖货营销线索 + 成交卖家
为什么问题 4 要挂在问题 3 后面 因为我一开始有一个假设：复购率低，肯定是体验差（物流慢、给差评），客户不爽就不来了。 问题 4 就是为了验证（或者推翻）这个假设。 结果是推翻了——92% 的订单提前送达、平均评分 4.29，绝大多数人体验是好的。 这个"假设被数据打脸"的过程，反而成了整个项目最有价值的一段（第 10 章问题 4）。

为什么是这五个，不是别的

电商经营分析有一个经典的拆解框架，几乎所有的题都能塞进这个三角形：

# 电商 GMV 的三因子拆解
GMV  =  用户数  ×  客单价  ×  复购频次
        │          │          │
        │          │          └── 问题 3（复购率 3.04%）
        │          └───────────── 问题 1（客单价跌 13.4%）
        └──────────────────────── 问题 5（营销拉新，但只贡献 5% GMV）

# 再加两个"分析质量"维度
问题 2  ── 结构性：钱集中在哪个品类（决定资源往哪投）
问题 4  ── 体验性：服务出问题会不会毁掉复购（验证因果，不是看相关）

这五个问题覆盖了规模、结构、留存、体验、获客五个面，正好是一个实习分析师 在面试里最容易被问到的五个方向。做透这五个，比做二十个花哨的图有用。

顺序不是随便排的 1 → 2 → 3 → 4 → 5 的顺序本身就是一条逻辑链：先看总量（盘子），再看结构（品类）， 再看留存（复购），然后验证留存的病因（体验），最后回到源头（获客质量）。 这条链走到最后会形成一个闭环——获客质量差 + 品类低频 + 体验其实不差 = 复购低是结构性的， 不是服务问题。这就是第 11 章那个结论的来路。

03四个工具各干什么

这四个工具不是"越多越好"，每个都有明确的分工，谁都不能替代谁。 下面这张表是我后来总结的，当时其实是踩了坑才想明白的。

工具在这个项目里干什么为什么非它不可
Excel 探索性分析：看字段、试口径、做透视表、画草图 改一个数、加一列、拖个透视，全都是一次点击的事。用它试错最快， 而且能看见数据长什么样（格子里就是真数据，不像代码只输出一个数）
Python
(pandas)		 固化口径：把 Excel 里试出来的规则写成脚本，产出 7 张底表 Excel 里的操作是"手工的"，关掉文件就没了，也没法给别人复现。 Python 脚本是可重复执行的——换一份数据，改个路径，跑一遍就是新结果。 另外：简历技能栏写了 Python，得有个项目撑住这句话
MySQL
(Navicat)		 多表关联 + 聚合：写 5 段 SQL 回答五个问题 数据分析岗面试必考手写 SQL。而且多表 JOIN 用 pandas 写出来是一长串 merge， 用 SQL 写就是一句 JOIN，可读性差一个量级。
更重要的是：SQL 的 JOIN 结果是可以被 .csv 验证的，行数对不对一眼就能发现
Tableau
Public		 出图 + 发布：6 张图拼成一块看板，发到网上拿公开链接 简历上放一个点得开的链接，比写十行"熟练使用可视化工具"有用。 而 Tableau Public 是唯一一个能免费无限发布公开看板的主流 BI 工具 （Power BI 免费版发不了公开链接，FineBI 要部署服务器）

为什么不用一个工具做到底

为什么不全用 Excel？

Excel 的上限在 100 万行左右，这个项目明细表 11 万行，其实扛得住。 但有两个问题：一是不可复现（我的透视表用了哪几列、筛选了什么条件，只有我自己知道， 换个电脑打开就散了）；二是没法放进 GitHub（仓库里放一个 xlsx，别人看不出你做了什么）。

为什么不全用 Python？

因为在还不确定要算什么的时候，写代码是最慢的。我在 Excel 里试口径的时候， 改一个 IF 条件、看一眼结果、再改，前后不到 10 秒；换成 Python 要改代码、切换窗口、重跑、看输出， 一个来回一分钟。探索阶段用 Excel，是把工具的切换成本降到最低。

这里有个我犯过的错，值得记下来 我一开始的计划是"用 Python 把数据完整摸一遍"，写完脚本跑出来一看，得到的所有数字 Excel 里早就有了。当时我的反应是"这不是白干吗"。

后来才想清楚：Python 这一步的价值不在于"算出新东西"，而在于"把已经算对的东西固定成可复现的流程"。 它交付的不是数字，是一个别人能跑的文件。想通这一点之后，我就把 Python 压缩成 1 个主脚本 + 5 个扩表脚本 + 1 个出图脚本，每个只干一件事，不再追求"用代码重做一遍"。

为什么 Tableau 不能直连 MySQL

Tableau Desktop 是可以的，但 Tableau Public 不行——它只能连静态文件（CSV、Excel）， 不能连数据库、不能用 ODBC。我试过，Public 版本的数据源类型里根本没有 MySQL 选项。

所以流程变成：Python 把底表导出成 CSV → Tableau Public 连 CSV → 发布。 CSV 就是"数据库和可视化工具之间的中转站"。

7.1 第 0 步：先把字段看清楚（这个脚本翻过一次车）

在动手算之前，先让程序把 11 张表的字段打出来。脚本是 py/q0_看字段.py。 第一版我写得很糟糕，直接用 print(df.head()) 把 DataFrame 原样打出来—— 结果 14 个字段在终端里连成一长串，被折行成竖着的乱码。

# ---- 第 0 步：先看看这批数据里到底有什么 ----
# 输出分两块，都是给人看的：
#   第一块：总览表（表名 / 行数 / 字段数 / 这张表是干嘛的）
#   第二块：每张表的字段清单，一行一张表

import pandas as pd, glob, os

# 这两行是让 pandas 别把输出截断（不写会变成 a...b 这种省略号）
pd.set_option("display.max_colwidth", None)
pd.set_option("display.width", 200)

base = r"D:\...\raw"

# 每张表是干嘛的 —— 用一句人话（字典，key 是表名）
note = {
    "orders": "订单主表：谁买的、什么状态、下单/发货/送达/承诺送达时间",
    "order_items": "订单明细：每件商品多少钱、运费多少、哪个卖家发的",
    "customers": "客户：客户编号 + 城市 + 州",
    "order_reviews": "评价：1-5 星 + 评论文字",
    ...
}

summary, detail = [], []
for f in sorted(glob.glob(base + r"\*.csv")):
    # 把文件名 olist_orders_dataset.csv 洗成 orders
    key = os.path.basename(f).replace("olist_", "") \
                             .replace("_dataset.csv", "") \
                             .replace(".csv", "")
    # 只读 3 行拿列名就够了，没必要把 100 万行读进来
    cols = list(pd.read_csv(f, nrows=3).columns)
    summary.append({
        "表名": key,
        "行数": f"{len(pd.read_csv(f, usecols=[0])):,}",  # 只数第 1 列，快
        "字段数": len(cols),
        "这张表是干嘛的": note.get(key, ""),
    })
    detail.append((key, " · ".join(cols)))   # 字段用 · 连起来，一行一张表

print("【第一块】11 张表总览 —— 哪张是主角，先看这一张")
print(pd.DataFrame(summary).to_string(index=False))

print("\n【第二块】每张表的字段清单")
for key, cols in detail:
    print(f"\n▸ {key}\n  {cols}")
这个脚本里有两个容易被忽略的细节 ① nrows=3 只为了拿列名。地理表有 100 万行，全读进来要几十秒， 而拿列名只需要前 3 行。探索阶段不要为了看一眼就全量读数据。
② usecols=[0] 只为了数行数。只加载第 1 列，内存和速度都省下来了。

这两条加起来，11 张表的扫描从"卡半天"变成"秒出结果"。

# 2. 口径一：取消 / 不可用 / 未付款的订单，不算钱
# .astype(int) 把 True/False 转成 1/0，这样 SQL 里可以直接写 is_valid = 1

~ 取反我们要的是"不在这三个词里"的单，所以取反
.astype(int)把 True/False 变成 1/0，因为写入 CSV 再导入 MySQL 时，True/False 会变成字符串，而 1/0 能被 MySQL 认成整数，可以直接做 SUM

第 3 段：口径二 —— 归月用哪个时间

就是这里，astize 改成 1/0 之后我踩了一个坑 起初我用布尔值做筛选：t_item[t_item["is_valid"]]。 后来把 is_valid 改成 1/0 存进 CSV，再读回来就变成了整数， 于是这行报 KeyError: "None of [Index([1,1,1...])] are in the [columns]"。

    if x == 0:  return "2_准时"

8.1 建库：一个项目一个库，别混在老库里

打开 Navicat → 右键「MySQL」连接 → 「新建数据库」。库名 olist，字符集 utf8mb4， 排序规则 utf8mb4_0900_ai_ci。

-- 如果习惯用命令，等价于这两行
CREATE DATABASE olist
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;

USE olist;
为什么一定要 utf8mb4，不是 utf8 MySQL 里的 utf8 是假的 utf8，最多只存 3 个字节，存不了 emoji 和部分生僻字。 utf8mb4 才是完整的 4 字节 UTF-8。这条不是洁癖——商品品类名、城市名里出现特殊字符时， utf8 会直接报错或者截断。

8.2 七张表怎么建（DDL 全文）

Navicat 的「导入向导」能自动猜表结构，但它猜得很差（第 8.7 节会看到它把日期猜成什么样）。 所以我选择先手写建表语句，再往里灌数据——字段类型自己定，不留后患。

-- ① 底表 A：订单（一行 = 一个订单）
CREATE TABLE order_base (
  order_id      VARCHAR(40)  PRIMARY KEY,
  customer_id   VARCHAR(40),
  order_month   VARCHAR(7),
  order_status  VARCHAR(20),
  is_valid      INT,
  delay_days    INT
);

-- ② 底表 B：订单明细（一行 = 一件商品，一个订单会有多行）
CREATE TABLE order_item_base (
  order_id                     VARCHAR(40),
  product_id                   VARCHAR(40),
  seller_id                    VARCHAR(40),
  price                        DECIMAL(10,2),
  freight_value                DECIMAL(10,2),
  product_category_name_english VARCHAR(60),
  order_month                  VARCHAR(7)
);

-- ③ 底表 C：客户（customer_id 是"一次下单"，customer_unique_id 才是"人"）
CREATE TABLE customer_base (
  customer_id        VARCHAR(40) PRIMARY KEY,
  customer_unique_id VARCHAR(40),
  customer_state     VARCHAR(2)
);

-- ④ 底表 D：评价（一个订单只留一条）
CREATE TABLE review_base (
  order_id     VARCHAR(40) PRIMARY KEY,
  review_score INT
);

-- ⑤ 底表 E：渠道（一行 = 一条营销线索）
CREATE TABLE channel_base (
  mql_id             VARCHAR(40) PRIMARY KEY,
  seller_id          VARCHAR(40),
  first_contact_date VARCHAR(10),   -- 故意用字符串，见 8.7
  origin             VARCHAR(30),
  is_won             INT,
  won_date           VARCHAR(10),   -- 同上
  business_segment   VARCHAR(50)
);
字段类型为什么是它如果选错的后果
VARCHAR(40)Olist 的 ID 是 32 位十六进制字符串（md5 样式），40 留点余量用 INT 会全部变 0，因为字符串转数字失败
DECIMAL(10,2)金额必须精确到分，10 位整数 + 2 位小数够用到亿级用 FLOAT 会出现 13494400.739999998 这种鬼数，对账永远差几分
VARCHAR(7)月份存成 2017-11，7 个字符正好存成 DATE 要补 01 号，GROUP BY 的时候还得再截断一次
INT（is_valid / is_won）0 / 1 标记，能直接 SUM() 出计数存成 '是'/'否' 就没法求和，得套 CASE WHEN
一个反直觉的选择：日期存成字符串 底表 E 的两个日期（first_contact_date、won_date）我故意用 VARCHAR(10) 存， 不是 DATE。原因见 8.7，那是我这次踩得最惨的一个坑， 栽进去之后整张表 8,000 行一条都导不进去。

8.5 问题一：这个盘子到底有多大

要回答的是"两年多时间，平台卖了多少、走了多少单、每单多少钱、有没有在变好"。一句话： 按月看 GMV、订单数、客单价。

SELECT
    order_month,
    ROUND(SUM(price), 2)                        AS gmv,
    COUNT(DISTINCT order_id)                    AS order_cnt,
    COUNT(*)                                    AS item_cnt,
    ROUND(SUM(price) / COUNT(DISTINCT order_id), 2) AS aov
FROM order_item_base
GROUP BY order_month
ORDER BY order_month;

逐行讲

order_month分组依据。因为底表 B 里只保留了有效订单（Python 阶段已经过滤过），所以这里不用再写 WHERE。
SUM(price)把明细行的商品金额加起来。注意是 price 不含 freight_value——运费不算 GMV，这是全篇最重要的一个口径。
ROUND(..., 2)保留两位小数，否则会出来 1003862.1400000001 这种。
COUNT(DISTINCT order_id)本段唯一的技术点。一个订单有三件商品就是三行，直接 COUNT(*) 会把订单数放大 14%（112,101 vs 98,199）。加 DISTINCT 才是"多少个订单"。
COUNT(*)数明细行数（多少件商品）。这个数不能当订单数用，但可以用来算连带率：112,101 / 98,199 ≈ 1.14。
SUM(price) / COUNT(DISTINCT order_id)客单价。分子分母必须同源：分子是这批订单的商品总额，分母是同一批订单的订单数。
GROUP BY order_month按月份分组。因为 order_month 是 2017-11 这种格式，字符串排序天然等于时间排序，不用转 DATE。
ORDER BY order_month不写这句，MySQL 返回的顺序是不保证的，出图会乱。
这里有个必须当场说清楚的差异 订单表（底表 A）里有效单是 98,202，明细表（底表 B）里算出的是 98,199，差 3 单。 原因不是算错，是有 3 个有效订单没有任何商品明细行——订单创建了、状态正常，但一条 item 都没记录。 这类订单连"卖了多少钱"都无从谈起，所以在以 GMV 为主指标的场景里，以明细表为准。 这句话要能主动说出来，它证明你真的逐行核过数，而不是抄了别人的结论。

这个查询给出的三个事实

13,494,400.74两年有效 GMV（R$）
98,199有效订单数
137.42整体客单价（商品口径）
-13.4%客单价从 2017-01 到 2017-12
  1. 盘子是真在长。2017-01 月 GMV 120,098.27，2017-11 冲到 1,003,862.14，涨了 8.4 倍。
  2. 但每一单越来越便宜。2017-01 客单价 152.60 → 2017-11 的 135.27 → 2017-12 的 132.11，跌 13.4%。
  3. 同期订单数涨得更快：787 → 7,421，9.4 倍。单量涨得比 GMV 快，数学上就只能是客单价在跌。

这三条一摆出来，问题一的答案就有形状了：不是"平台在健康增长"，是"靠低价商品冲量在增长"。 后面四个问题都是在追这个判断的证据。

8.6 问题二：钱是从哪几个品类来的

按品类聚合 GMV，看集中度。CR5（前五名占比）是零售分析的常规指标—— 如果 CR5 很高说明有几根柱子撑着，如果很低说明是长尾，两种结构的建议完全相反。

SELECT
    product_category_name_english                AS category,
    ROUND(SUM(price), 2)                       AS gmv,
    COUNT(DISTINCT order_id)                   AS order_cnt,
    COUNT(*)                                   AS item_cnt,
    ROUND(SUM(price) / COUNT(*), 2)           AS avg_price
FROM order_item_base
GROUP BY product_category_name_english
ORDER BY gmv DESC
LIMIT 10;
注意 avg_price 的算法和上一问不一样 问题一的客单价是 SUM(price) / COUNT(DISTINCT order_id)（每单多少钱）； 这里的平均单价是 SUM(price) / COUNT(*)（每件商品多少钱）。 分母不同，含义就不同。写错这两个，会把 137 的客单价和 130 的商品均价说成一回事。

8.7 问题三：客户为什么不回头

这一问的 SQL 是全篇结构最复杂的一句，也是面试最爱问的一句。 难点不在语法，在 ID 选错——用 customer_id 算复购率，结果永远是 0，而且你不一定能发现。

SELECT
    COUNT(*)                                              AS 客户总数,
    SUM(CASE WHEN order_cnt >= 2 THEN 1 ELSE 0 END)    AS 复购客户数,
    ROUND(SUM(CASE WHEN order_cnt >= 2 THEN 1 ELSE 0 END)
          / COUNT(*) * 100, 2)                              AS 复购率
FROM (
    SELECT
        c.customer_unique_id,
        COUNT(DISTINCT o.order_id) AS order_cnt
    FROM order_base o
    JOIN customer_base c ON o.customer_id = c.customer_id
    WHERE o.is_valid = 1
    GROUP BY c.customer_unique_id
) t;

为什么必须套一层子查询

因为要算的是"每个人下了几单"，然后才能判断"几单算复购"。 这两件事是两个粒度：

1先按"人"聚合每人下过几单（内层查询）
2再按"人"计数多少人、多少人 ≥2 单（外层查询）

在一条 SQL 里跨两个粒度，只能用子查询（或者 CTE，但为了保持"最基础语法"我没用 CTE）。

逐行讲

c.customer_unique_id分组的依据。这个字段才是"人"。它来自客户表，所以必须先 JOIN 进来——订单表里只有 customer_id。
COUNT(DISTINCT o.order_id)数这个人下过几个不同的订单。加 DISTINCT 是因为订单表本身一个订单一行，不加也"碰巧"对，但加了更保险。
FROM order_base o主表是订单表（98,202 条有效单），因为"下过几单"的信息在这里。
JOIN customer_base c ON o.customer_id = c.customer_id把"人"的 ID 接进来。这里用 JOIN 不用 LEFT JOIN 也可以，因为客户表 100% 覆盖（不存在孤儿订单），实测 JOIN 前后行数不变。
WHERE o.is_valid = 1只算有效订单。取消的、缺货的不算"这个人买过一次"。
GROUP BY c.customer_unique_id按人聚合，得到"每人几单"。
COUNT(*)（外层）数子查询返回了多少行 = 有多少个客户。
SUM(CASE WHEN order_cnt >= 2 THEN 1 ELSE 0 END)条件计数。SQL 没有 COUNT(IF)，标准写法就是 CASE WHEN 出 1/0 再 SUM。
MySQL 里 SUM(order_cnt >= 2) 也能跑，但不是标准 SQL，换到 PostgreSQL 就报错，面试别写。
/ COUNT(*) * 100转成百分比。先除再乘，顺序不能反（反了整数除法会截断，虽然 MySQL 里 / 是浮点除法，但换到别的库会翻车）。
如果用 customer_id 会怎样（一定要试一次） 把 c.customer_unique_id 全换成 o.customer_id 再跑一遍， 你会发现客户总数变成 98,202，复购客户变成 0，复购率 0.00%。 因为 customer_id 是跟着订单生成的，一个人买两次就有两个 ID， 按它分组，每组永远只有一单——复购率在数学上不可能不是 0。 这个错误极其隐蔽：SQL 不报错、结果是个"合理"的百分比，只有你知道 3% 才是真的，才抓得住。

8.8 问题四：体验差是不是复购率低的原因

这是我原本的假设：物流慢 → 体验差 → 不复购。看起来天经地义，但数据把这个假设打了。 要验证它，得把"延迟天数"分档，看每档的差评率。

SELECT
    CASE
        WHEN o.delay_days < 0  THEN '1_提前送达'
        WHEN o.delay_days = 0  THEN '2_准时'
        WHEN o.delay_days <= 3 THEN '3_延迟1-3天'
        WHEN o.delay_days <= 7 THEN '4_延迟4-7天'
        ELSE                       '5_延迟7天以上'
    END AS 延迟区间,
    COUNT(*) AS 订单数,
    ROUND(AVG(r.review_score), 2) AS 平均评分,
    ROUND(SUM(CASE WHEN r.review_score <= 2 THEN 1 ELSE 0 END)
          / COUNT(*) * 100, 2)      AS 差评率
FROM order_base o
JOIN review_base r ON o.order_id = r.order_id
WHERE o.is_valid = 1
GROUP BY 延迟区间
ORDER BY 延迟区间;

逐行讲（只讲新东西）

CASE WHEN ... END AS 延迟区间分档函数。顺序很重要：SQL 从上往下匹配，命中一个就停。所以 < 0 必须写在最前面，否则会被后面的 <= 3 抢走（负数也满足 <= 3）。
'1_提前送达' 这个前缀文字前面加数字，是为了让 ORDER BY 排序正确。不加的话，按拼音排会变成"延迟1-3天、提前送达、准时……"，图就没法看了。这是个小技巧，但很实用。
AVG(r.review_score)平均评分，1~5 分。看趋势有没有单调性。
WHEN r.review_score <= 2 THEN 1 ELSE 0差评的定义。我选 ≤2（而不是 ≤3），因为巴西电商 3 星算中性评价，把它算成差评会虚高。口径要说出来，别让别人猜。
JOIN review_base r ON o.order_id = r.order_idINNER JOIN。只保留"有评价的订单"。注意：不是所有订单都有评价，所以基数会从 98,202 掉到 95,830。这个变化必须在文档里交代，不然数字对不上。
GROUP BY 延迟区间可以直接用 SELECT 里的别名分组（MySQL 支持）。标准 SQL 不允许，写 GROUP BY CASE WHEN ... 更保险，但太长了。

但这个结果推翻了我的原始假设

92.0%订单是"提前送达"
1.3%刚好准时（0 天）
6.7%延迟超过 1 天
79.30%延迟 7 天以上的差评率
  1. "延迟"根本不是普遍现象。92% 的订单提前送到了，平均评分 4.29。 所以"物流差导致大家不回头"这个假设，对绝大多数客户不成立——他们体验是好的。
  2. 承诺时间给得太宽松了。只有 1.3% 是刚好准时，说明平台承诺的送达日留了巨大缓冲。 "提前送达"是常态，这本身是一个被低估的指标。
  3. 延迟是"小概率、高杀伤"。延迟 >7 天的订单只占 2.9%，但差评率 79.3%； 这部分订单贡献了大约 32% 的差评，却只占 6.7% 的单量。
这一问真正的价值：一个被数据推翻的假设 面试官最爱听的不是"我做对了什么"，是"我原来想错了什么，数据怎么把我打醒的"。 这个反转就是最好的素材：物流是复购率低的"背锅侠"， 它解释不了 96.96% 的人只买一次。真因得往别处找——低频品类 + 拉新质量（下一章说）。

8.9 问题五：842 个签约卖家，是怎么来的

这条线是"营销 → 销售 → 卖家"的漏斗。线索表 8,000 条，成交表 842 条，按 mql_id 关联， 每条线索打上 is_won 标记（1 = 签约了）。

SELECT
    origin,
    COUNT(*)                                        AS leads,
    SUM(is_won)                                     AS won,
    ROUND(SUM(is_won) / COUNT(*) * 100, 2)          AS rate,
    ROUND(AVG(DATEDIFF(won_date, first_contact_date)), 1) AS avg_days
FROM channel_base
GROUP BY origin
ORDER BY rate DESC;
SUM(is_won)这就是把标记设计成 0/1 的好处。不用写 CASE WHEN，直接 SUM 就是"签约了几条"。如果当初存的是 '是'/'否'，这里就得套一层转换。
DATEDIFF(won_date, first_contact_date)签约日 - 首次接触日 = 签约周期（天）。DATEDIFF 两个日期，返回天数差。
DATEDIFF 为什么能跑因为这两列是 VARCHAR(10) 存的 2018-02-01 格式，MySQL 会隐式转成日期。空值返回 NULL，AVG 会自动跳过 NULL，不报错。
ORDER BY rate DESC按转化率从高到低排。别按 leads 排——线索量多不代表质量好。

这是整个项目最有杀伤力的一段话 营销团队招了 8,000 个线索、签了 842 个卖家，其中 463 个（54.99%）从签约到现在一单都没卖出去。 真正在卖货的 379 个卖家，两年加起来只做了 674,005.39 的 GMV， 占全平台 13,494,400.74 的 4.99%。

翻译成人话：营销是"重签约、轻激活"——签约数上去了，KPI 完成了，但对 GMV 的实际贡献只有 5%。 这不是分析师的措辞，这是业务诊断。这句话说出口，面试官会抬头看你。

8.10 这一阶段踩的坑：一张表 8,000 行，一个字都进不去

这是整个项目最像"真实工作"的一段。前六张表都顺顺利利，到第七张 channel_base （底表 E）突然全错，8,000 条报错 8,000 条。

根因：Navicat 的日期推断 + MySQL 的严格模式

1CSV 里日期是空的底表 E 的 won_date 对没签约的线索本来就是空的（8,000 条里只有 842 条有值）
2向导把空值转成 0000-00-00这是 MySQL 的"零日期"，一个历史上允许的脏值
3严格模式拒绝整行sql_mode 里含 NO_ZERO_DATE 时，0000-00-00 直接判非法，整行丢弃
48,000 行全中招因为每一行都有日期列，没签约的行是空，签约的行也可能被猜错

我试了三轮才通：

尝试做法结果
①把列改成 VARCHAR(10) 再导仍然失败——表结构改了，但 CSV 里那两个字段还是有空值被塞成 0000-00-00 的字符串
②干脆把这俩日期列从底表 E 里删掉重新生成导入成功，但代价是签约周期的分析没了
③把日期列加回来，全程按 VARCHAR(10) 字符串处理（脚本里只切前 10 位，不做日期转换）最终方案，8,000 行全进，DATEDIFF 靠 MySQL 隐式转换照样能算
这个坑的三条教训（面试可以直接讲）
  1. 导入失败不要先怀疑数据脏，先看日志第一行。 日志里明明白白写着 '0000-00-00'， 我一开始在编码和分隔符上折腾了半天，全是白费。
  2. "能导进去"和"能用来分析"是两件事。 第 ② 轮我把日期列删了，确实通了， 但问题五的"签约周期"就没了。为了跑通而丢字段，等于把问题砍掉一半。

10.1 问题一：这个盘子到底有多大

口径数值怎么算的什么时候用
GMV（商品口径）13,494,400.74SUM(price)，只算有效订单本文全篇统一用这个

为什么 GMV 不含运费（这个必须能解释） 三个理由： ① 运费是物流成本转嫁，不是商品价值，把它算进 GMV 会高估平台经营能力； ② 运费跟品类强相关（大件家具运费高），算进去会扭曲品类之间的比较； ③ 行业惯例（GMV 通常指商品交易总额，不含履约费用）。

但两种口径都要能报出来——面试官问"含运费多少"，答不出来说明你没算过。

11.1 结论一：这是"拉新 + 低价冲量"的增长，不是复购驱动的增长

1单量涨 9.4 倍787 → 7,421 单/月
2客单价跌 13.4%152.60 → 132.11
3复购率 3.04%96.96% 只买一次

三个数一起看，只有一个解释：平台在用"更便宜的商品"拉"更多的新客户"。 新客户买完就走，所以 GMV 靠不断拉新维持，而不是靠老客户重复购买。

这种增长的问题在哪（这是分析的落点） 获客成本一旦上升，增长立刻失速。 因为它没有"老客户复购"这个免费的增长引擎——每多做一块钱 GMV，都要重新买一次流量。

而且客单价在跌，意味着同样的获客成本，能收回的钱越来越少。 两条曲线（成本升、单价降）迟早交叉，交叉点就是亏损点。

这句话可以直接念："这个平台的增长是买来的，不是长出来的。"

11.5 为什么必须算 ROI：不算，就会砍错渠道

第 11.3 节得出「842 个签约卖家里 54.99% 从未出单」。 直觉的反应是：那就少签点、签准点。 但「签得准」是一个过程指标，它回答不了「钱该不该继续投」。

举个具体的例子。看 social 这个渠道：

签约数75 家　全部渠道第 4 多
转化率5.56%　倒数第 4
每条线索带来的 GMV32.16 R$　倒数第 4
每条线索带来的平台收入4.82 R$　倒数第 4

如果只考核「签约数」，social 排第 4，看起来还行，预算会继续投。 如果考核「转化率」，它排倒数第 4，会被判成「再优化优化」。 但真正的答案是：这个渠道在任何合理的获客成本下都是亏的—— 4.82 R$ 是它的收入上限，而一条 B2B 卖家线索的获客成本不可能低于 5 R$。

这就是 ROI 存在的唯一理由 「产出低」有两种完全不同的含义：一种是这个渠道不行，另一种是它便宜。 只有把产出换算成平台收入、再和获客成本放在一起比，才能回答「停不停」。

不做这一步的后果很具体：指标停在过程中间，钱就停在错误的渠道上。 这正是 11.3 节说的「重签约、轻激活」—— 它不是某个人的失职，是考核指标只到签约那一步，后面的价值没人算。

11.6 ROI 三步：从 GMV 走到「盈亏平衡获客成本」

ROI = (收益 − 成本) / 成本。这份数据缺成本，但缺成本不代表算不了—— 可以反过来算：成本最多能到多少，这笔投放才不亏。 这个数叫盈亏平衡获客成本（breakeven CPL），是投放决策里真正被用的那个数。

步算什么公式这一步解决什么
①GMV → 平台收入GMV × 佣金率GMV 不是平台的钱，抽成才算收入
②收入 → 每线索收入渠道收入 ÷ 线索数这是这个渠道的盈亏平衡 CPL
③CPL 敏感性ROI = (每线索收入 − CPL) ÷ CPL不知道真实 CPL，就列一张表让别人自己查
佣金率是假设值，必须说清楚 数据集里没有佣金率。市场型电商的行业区间大约 10%~20%， 这里主口径取 15%，并做三档敏感性。这不是数据算出来的，是我引入的外部参数—— 面试时必须主动说这一句，否则被追问「佣金率哪来的」会很难看。

11.7 A/B 实验：为什么观察数据答不了这个问题

第 11.2 节的结论是「长尾结构决定了不能砍品类，只能调单价结构」， 抓手是 watches_gifts——它的平均单价 200.70，是 bed_bath_table（93.36）的 2.15 倍。 于是很自然会想：那就在推荐位上多推 watches_gifts，客单价不就上去了？

这句话在观察数据上无法验证，而且很可能是错的。三个原因：

问题在这个项目里具体是什么后果
选择偏差买 watches_gifts 的人本来就更有钱。是「有钱」导致「买表 + 客单价高」，不是「买表」导致「客单价高」把相关性当因果，推了推荐位却没效果
无法归因推荐位挤占了页面空间，可能让原本要买的便宜商品被挤出，总成交反而下降只看客单价会漏掉转化率的损失
不能证伪历史数据里没有「不推」的那批人，没有对照组，任何结论都只是一家之言面试官一句「你的对照组哪来的」就结束
所以实验不是「加个彩头」，是唯一能回答这个问题的方法 没有随机化，就没有反事实。没有反事实，「推了推荐位客单价涨了 8%」 这句话永远无法排除「那两周本来就在涨」。

这也解释了为什么简历上写「熟悉 A/B 测试」很容易被问穿—— 面试官真正想确认的不是你会不会算样本量， 而是你知不知道什么结论必须靠实验才能下。

11.8 实验设计：先把问题问对，再算样本量

第一步：把问题反过来问（反向 MDE）

绝大多数人算样本量的方式是：「我想检测 5% 的提升，需要多少样本？」 这个问题问错了。因为它默认了「5% 这个精度值得等」， 而这个平台日均只有 154 单，想检测 5% 要跑 189 天——半年，没人会批。

正确的问法是：「我只跑 21 天，能看出多大的提升？」 这就是最小可检测效应（MDE），由样本量和方差反推出来，不是拍脑袋定的。

第三步：护栏指标要选「不滞后的」

21 天的实验，连差评率涨 3 个百分点都看不出来。 更何况评价本身是滞后的——用户收到货才会评，实验结束那天评价还没回来一半。

所以护栏要换成当天就能观测的指标 延迟订单占比、准时率、发货时长——这三个不用等用户评价， 订单一旦超时就能算出来。差评率放到实验结束后 30 天的回看做，不进实验中期的红线。

这是「护栏指标必须和观测窗口匹配」的具体案例， 比笼统地说「要注意体验」有用得多。

第一步把问题反过来问。常规做法是问『想检测 5% 提升需要多少样本』， 但这个平台日均只有 154 单，算下来要 189 天，半年，没人会批。 所以我改成问『我只跑 21 天，能看出多少』——答案是 15.0%。

它没有执行，因为数据是历史二手的。但我能说清什么情况下它值得执行、什么情况下不值得。」

这段会被追问的四句话

追问怎么答
「你为什么不直接给建议？」建议需要因果，数据只能给相关。我要先确认这件事值不值得验证——如果连检测 10% 都要半年，这个改动本来就不该上。先算可行性，再谈建议。
「样本量公式你还记得吗？」连续型的公式是 n = 2 × (z<sub>α/2</sub> + z<sub>β</sub>)² × σ² / δ²。双尾 α=0.05、power=0.8 时，(z+z)² = 7.849。δ 就是最小可检测效应，我是反过来由它解出 21 天对应的检测力的。
「CUPED 为什么用不了？」CUPED 要有实验前的历史数据做协变量。这个平台复购率 3.04%，96.96% 的客户一辈子只下一单，没有「实验前」这个概念。这也是为什么我只能退而用截尾和分层——它们的代价我都写清楚了。
「那什么时候这实验能做？」两个条件满足一个：日均订单翻到 500 单以上；或者复购率做到 20% 以上，CUPED 能用起来。在这之前，用整月切换策略加前后对比，别硬做精细化实验。
这三个「答不上」是加分项，不是扣分项 ① CUPED 用不了、② 差评率当护栏看不到、③ 检测 5% 要半年不可行。 这三件事说出来，比任何成功案例都更能证明你是真做过的—— 没动手的人不知道哪里会卡。

但前提是你要能答出「为什么卡、卡在哪、能不能绕过」这三层。 只说「做不了」会显得没能力，说清「为什么做不了，以及什么条件下能做」才是判断力。

Q1　简单介绍一下这个项目

问"简历上这个巴西电商的项目，你简单说一下。"
答 "这是我用 Olist 公开数据集做的平台经营分析。数据是 2016 年 9 月到 2018 年 8 月的 9.9 万个订单、1,349 万雷亚尔 GMV。

我提了五个问题：盘子多大、钱从哪来、客户为什么不回头、体验差是不是原因、卖家从哪来。

最后串出来的结论是：这个平台的增长是靠拉新和低价冲量买来的，不是靠复购长出来的—— 单量涨了 9.4 倍，但客单价跌了 13.4%，复购率只有 3.04%。"
追问通常会追问"3% 你怎么算的" → 转到 Q6。

Q2　为什么用这个数据集，不用淘宝那个

问"我看你之前写的是淘宝用户行为分析，为什么换掉了？"
答 "淘宝那个数据集只有行为日志——点击、收藏、加购，没有金额、没有订单、没有评价。 所以只能做转化漏斗，做不了 GMV 拆解，也做不了复购和物流分析。

Olist 不一样，它是真实的多表交易数据，有订单、明细、客户、评价、卖家、物流时间， 能支撑五个业务问题，而且表之间有关联，能练 JOIN。

更实际的原因：淘宝那个数据集很多人用过，面试官一年能看几十份。 我想拿一个别人不容易讲出花的。"
追问"Olist 也很多人用" → 答："是，但大多数人只算 GMV 和品类。 我做了物流-评价关联和渠道僵尸卖家，这两个角度少见。"

Q3　为什么剔除 canceled / unavailable / created

问"订单状态那么多，你为什么只留这几个？"
答 "因为这三种状态没有产生真实交易。

canceled 是取消，钱退了；unavailable 是缺货， 货没发出去；created 是订单刚创建，还没进入履约。

如果一个客户下单了但被取消，他没买到东西，这笔钱不能算 GMV， 也不该算"他买过一次"。把它算进去，GMV 会虚高，复购率也会虚高。

具体到数字：全部订单 99,441，剔掉这三种之后是 98,202 有效订单。 最多的一个月是 2017-11，7,544 单里剔了 123 单（unavailable 84 + canceled 37 + created 2）。"
追问"shipped / invoiced 为什么留着？" → 答："这两个已经付款、进入履约了，只是还没签收。钱是真的收了，算 GMV 没问题。"

Q4　为什么 GMV 不含运费

问"运费为什么不加进去？"
答 "三个理由。第一，运费是履约成本，不是商品价值， 它代表"把货送过去花了多少钱"，不代表平台卖货的能力。 第二，运费跟品类强相关——大件家具运费高，算进去会让品类之间的比较失真。 第三，GMV 的行业定义是商品交易总额，本身就不含履约费用。

但我两种口径都算了：商品口径 13,494,400.74，客单价 137.42； 含运费 15,735,527.03，客单价 160.24。差 2,241,126，就是两年运费总额。"
追问这题答完通常不追了，因为两种口径都报了。

Q5　订单数为什么不能直接 COUNT(*)

问"你这个表一个订单几行？"
答 "一个订单可能多行——买三件商品就是三行。所以明细表是 112,101 行， 但实际只有 98,199 个订单。

如果直接 COUNT(*)，订单数会多算 14%，客单价就会少算 14%。 正确的写法是 COUNT(DISTINCT order_id)。

这个数还有别的用处：112,101 / 98,199 = 1.14，就是连带率， 平均每单 1.14 件商品。"
追问"那客单价的分子是什么？" → 答："分子是这批订单的商品总额，必须是同一批订单。分子分母不同源，算出来的客单价没有意义。"

Q6　customer_id 和 customer_unique_id 有什么区别

问"你复购率怎么算的？"
答 "这里有个坑，我一开始也差点踩。

customer_id 看起来像客户编号，其实它是跟着订单生成的—— 同一个人买两次，会有两个不同的 customer_id。 而 customer_unique_id 才是"这个人"。

所以如果用 customer_id 分组，每组永远只有一单， 复购率在数学上不可能不是 0。而且 SQL 不报错、结果看着还挺合理， 非常隐蔽。

正确的做法是：订单表 JOIN 客户表拿到 customer_unique_id， 按它分组数每人几单。9.9 万个 customer_id 只对应 96,096 个人。 最后算出 94,986 个有有效订单的客户，其中 2,887 人复购，复购率 3.04%。"
追问"为什么客户总数是 94,986 不是 96,096？" → 答："因为只统计有有效订单的客户。96,096 是客户表全部的人，其中有一部分只有取消或未完成的订单。"

Q7　客单价在跌，是坏事吗

问"客单价跌 13.4%，你觉得是问题吗？"
答 "单看客单价跌，不能判断好坏。要看它跟单量的关系。

如果客单价跌、单量涨，可能是"降价换量"，短期看 GMV 还在涨，是策略选择； 如果客单价跌、单量也跌，那就是真的在衰退。

这个案例是第一种：客单价从 2017-01 的 152.60 跌到 2017-12 的 132.11， 同期订单数从 787 涨到 7,421，涨了 9.4 倍。 所以 GMV 还在涨。

但问题在于它不可持续——客单价持续下滑意味着每单赚的钱越来越少， 而获客成本不会跟着降。两条线迟早交叉。而且复购率只有 3.04%， 说明这些新客户买完就走，下一块钱 GMV 还得重新买流量。"
追问"那你会怎么建议？" → 答："两条腿。短期做连带率——现在只有 1.14，提到 1.3 就能多 14% GMV，不花钱；长期把流量往高单价品类倾斜，watches_gifts 单价 200.70，是 bed_bath_table 的 2.15 倍。"

Q8　复购率 3% 怎么看，正常吗

问"3% 的复购率，你觉得正常吗？"
答 "不正常，但我要先说清楚它为什么不正常。

第一，要跟品类比。家具、大家电这种低频品类，复购天然低，3% 不奇怪。 但 Olist 卖的主要是 bed_bath_table、health_beauty、sports_leisure 这些消耗品—— 床品会旧、美妆会用完、运动器材会磨损，这些品类本来该有复购。

第二，要跟同行比。中国电商整体复购率 30% 以上，成熟平台老客贡献 60% GMV。 巴西市场整体偏低，但成熟平台也在 20% 以上。

第三，看分布不看平均数。94,986 个客户里，92,099 人（96.96%）只买过一次， 买 4 次以上的只有 48 人。这不是"复购率偏低"，是几乎没有复购。

所以我不会说"3% 有点低"，我会说"这个平台基本没做留存"。"
追问"那你怎么不做一个 RFM 分层？" → 答："做不了。RFM 里 F 是购买频次，这里 96.96% 的人 F=1，分不出层。硬做出来的分层是假的。这是我在文档里明确写了的局限。"

Q9　物流延迟是不是复购率低的原因

问"你觉得客户不回头是因为体验不好吗？"
答 "我原来的假设就是这样，但数据把我打了。

我把订单按延迟天数分成五档看差评率，单调性非常干净： 提前送达的 9.22%，延迟 1-3 天 32.13%，延迟 4-7 天 67.56%， 延迟 7 天以上 79.30%。表面上完全支持"物流差导致差评"。

但关键是样本量：92% 的订单是提前送达的，平均评分 4.29， 只有 1.3% 刚好准时，延迟超过 1 天的只有 6.7%。

所以结论反过来了：绝大多数客户体验是好的，物流解释不了 96.96% 的人不回头。 物流真正的问题是"小概率高杀伤"——延迟超过 7 天的订单只占 2.9%， 却贡献了大约 32% 的差评。这值得改，但救不了复购。"
追问"那真因是什么？" → 答："低频品类 + 拉新质量。平台靠低价冲量拉来大量'只买一次便宜货'的客户，这些人本来就没有第二次需求。这不是物流问题，是增长方式问题。"

Q10　CR5 只有 39.77%，你会怎么建议

问"CR5 不到 40%，是不是品类太散了？"
答 "是散，但"散"不等于"该收"。

71 个品类，第一名只占 9.30%，前五名合计 39.77%， 后 66 个品类贡献了 60% 的 GMV。

如果 CR5 是 80%，最优策略是保头部、砍长尾。 但这里是 39.77%，砍长尾等于砍掉六成收入，这是最常见的错误建议。

我的建议不是"选哪个品类做重点"，而是调结构： 同样是卖，watches_gifts 单价 200.70、5,604 单做到 119 万； bed_bath_table 单价 93.36、9,399 单才做到 103 万。 把流量往高单价品类倾斜，客单价能拉回来，而且不用砍任何品类。"
追问"高单价品类单量少怎么办？" → 答："所以是倾斜不是转向。低单价品类用来拉新（转化率高），高单价品类用来做 GMV（客单价高），两个作用不冲突。"

Q11　这个项目里你遇到最大的困难是什么

问"做的过程中有什么卡住的地方？"
答 "最像真实工作的一段是导数据。

七张表里有六张顺利导入，第七张渠道表 8,000 行报错 8,000 条，一条都进不去。 我先怀疑编码、分隔符，折腾了半天没用。后来去看导入日志的第一行， 发现每一行里都有一段 '0000-00-00'——本该是日期的地方变成了零日期。

原因是这张表有两个日期列，没签约的线索那两列是空的， Navicat 把空值转成 0000-00-00，而 MySQL 严格模式拒绝这种值，整行丢弃。

我试了三轮：第一次把列改成字符串，还是失败； 第二次干脆把两个日期列删了重新生成，导入成功，但"签约周期"这个指标废了； 第三次把日期列加回来、全程按字符串处理，才既导进去又保住指标。

这件事教我的不是技术细节，是：能跑通不等于能交付。"
追问"为什么不直接改 MySQL 的 sql_mode？" → 答："可以，但那是改环境迁就数据。换台机器、换个人部署，问题还在。把数据做成不依赖环境的样子更稳。"

Q12　如果给你更多时间和数据，你会继续做什么

问"这个项目还有什么可以做的？"
答 "三个方向，按性价比排。

第一，算 CAC 和 LTV。 现在只能说"营销对 GMV 贡献 5%"， 但算不出"每个签约卖家花了多少钱"，因为数据里没有投放金额。 如果有，就能算出真正的 ROI，这是最有价值的一步。

第二，查那 463 个僵尸卖家。 他们分布在哪些品类、哪些州、什么规模？ 如果能定位到"哪类卖家签了不干活"，下次签的时候就能提前筛。

第三，做地域分析。 地理表有 100 万行邮编-经纬度， 我现在完全没用。如果要回答"该在哪个州建仓"，这张表就派上用场了。

至于预测，我不会做。 只有 24 个月数据，做时间序列预测样本太少， 做出来的东西自己都不信。"
追问这题答完一般就结束了，因为展示了"知道边界在哪"。

Q13　这个项目做了 ROI 吗

问"你做了渠道分析，那 ROI 呢？"
答 "数据里没有投放金额，所以我没有硬凑一个 ROI，而是反着算—— 算盈亏平衡获客成本：每条线索最多能花多少钱，超过就亏。

三步：GMV 乘佣金率（假设 15%）换成平台收入 101,100.81 R$； 除以 8,000 条线索，得全体盈亏线 12.64 R$；再按渠道拆，就得到每个渠道的成本上限。

结果很干净：social 4.82、email 2.58、display 1.17， 这三条在任何合理 CPL 下都是亏的——不是"需要优化"，是"没有投放价值"。 可投放渠道里最好的是 paid_search，14.45 R$。

因为不知道真实 CPL 是多少，我又做了一张 5 / 10 / 20 / 50 四档的敏感性表。 市场部只要报一个成本数字，直接查表就知道该停哪个渠道，不用再找我算一遍。

最后做了个预算重分配模拟：把 display + email + social 的 1,961 条线索预算挪到 paid_search， 收入从 7,923.90 涨到 28,336.45，+258%。 但这个数我自己先打了折——它假设单位产出不变，现实里加投一定边际递减， 所以只能当方向，不能当预算。"
追问一"佣金率哪来的？" → 答："外部假设，不是数据算出来的。" 行业区间 10%~20%，我取 15%，还做了三档敏感性。 这点必须在开头就讲清楚，否则整张表的可信度都会被质疑。
追问二"有真实投放金额你会怎么改？" → 答："把这列填进 CPL，敏感性表直接变成 ROI 表，一张表出结论，不用重算。"

Q14　这个项目做了 A/B 测试吗

问"你会做 A/B 测试吗，这个项目里做了吗？"
答 "没执行，但做了一份可以直接交给工程的方案—— 数据是历史二手数据，没有对照组、没有随机化，硬做就是伪实验。

设计里有四件事：
① 反向 MDE。大多数人算"想检测 5% 要多少样本"，这个问法在我们这儿没意义， 日均只有 154 单。反过来算：跑 21 天，能看出 15.0% 的提升。
② 方差缩减。订单金额 σ=209.31、变异系数 1.52，根子是极端大单。 截尾到 P99 把 σ 压到 155.34，样本量省 40%；再按品类分层省约 12%。 两个一起用，检测 10% 从 47 天降到 25 天，21 天的可检测效应从 15.0% 降到 10.9%， 刚好越过"值得做"的门槛。
③ 护栏指标。本来想用差评率，一算不行：基线 12.80%， 要看出涨 3 个百分点得跑 28 天，21 天根本看不到，而且评价本身还滞后。 所以护栏换成延迟订单占比、准时率这些当天能算的，差评率放到实验后 30 天回看。
④ 分流单元。复购率只有 3.04%，按客户分流等于浪费流量； 但为了同一个人不在两边比价，分流仍按 customer_unique_id 哈希， 分析单元是订单。一人多单理论上要用聚类稳健标准误， 不过复购率这么低，影响不到 4%，可以按独立样本算。

最后一个坑：CUPED 用不了——96.96% 的客户没有历史订单，没有协变量可做。"
追问"为什么必须先做实验，不能直接上推荐位？" → 答："因为'watches_gifts 单价 200.70 是 bed_bath_table 的 2.15 倍'这个结论有选择偏差—— 买表的人本来就有钱。直接推很可能只提高曝光、不提成交， 甚至因为挤占页面把整体转化拉下来。这个只有随机化能分离。"
